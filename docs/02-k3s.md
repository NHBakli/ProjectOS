# 2. Installer K3s

## Ce que fait le rôle Ansible

| Sur le VPS | Changement |
|---|---|
| Modules noyau | Charge `overlay` et `br_netfilter` (aussi au démarrage) |
| Réseau | Active `ip_forward` |
| UFW | Autorise les réseaux internes du cluster (`10.42.0.0/16`, `10.43.0.0/16`), ouvre 80 et 443 |
| K3s | Binaire `v1.37.1+k3s1` vérifié par SHA-256, config protégée, service systemd |
| Traefik | Activé : il reçoit le trafic web sur 80/443 |

Le rôle ne touche **pas** à SSH, aux comptes ni à Fail2ban. Il ne réinitialise jamais le pare-feu.

## Sécurités intégrées

Le rôle refuse de s'exécuter si :

- l'approbation manque (fichier `k3s-approval.yml`) ;
- le système n'est pas Ubuntu 24.04 ;
- un autre K3s, non installé par ce projet, est déjà présent ;
- le port 6443 est déjà utilisé.

## Étapes

Prépare d'abord ton poste : [01-poste-local.md](01-poste-local.md). Garde une **2ᵉ session SSH ouverte** pendant l'installation, au cas où.

**1. Tester les prérequis** (lecture seule)

```bash
ansible-playbook -i ~/.config/projectos/hosts.yml \
  infrastructure/ansible/playbooks/prerequisites.yml
```

Sur un serveur neuf, `BLOCKED` est normal. Le rôle corrige ce qui manque à l'étape suivante.

**2. Installer**

```bash
ansible-playbook -i ~/.config/projectos/hosts.yml \
  -e @$HOME/.config/projectos/k3s-approval.yml \
  infrastructure/ansible/playbooks/install-k3s.yml
```

Relance la même commande. **Attendu :** `changed=0`.

**3. Vérifier**

```bash
ansible-playbook -i ~/.config/projectos/hosts.yml \
  infrastructure/ansible/playbooks/verify-k3s.yml
```

**Attendu :** `ready_nodes: 1`, `failed=0`.

**4. Tester le réseau et le stockage** (crée des ressources de test)

```bash
ansible-playbook -i ~/.config/projectos/hosts.yml -e k3s_smoke_tests_approved=true \
  infrastructure/ansible/playbooks/smoke-k3s.yml
```

**Attendu :** `DNS interne, HTTP via Service et lecture du PVC ... : réussis`.

Nettoyer ensuite :

```bash
ansible-playbook -i ~/.config/projectos/hosts.yml -e k3s_smoke_cleanup_approved=true \
  infrastructure/ansible/playbooks/cleanup-smoke-k3s.yml
```

**5. Contrôler depuis l'extérieur** (depuis ton poste)

```bash
for p in 22 80 443 6443 10250; do nc -vz -w5 <IP_VPS> $p; done
```

**Attendu :** 22, 80 et 443 répondent. 6443 et 10250 **expirent**.

## Utiliser kubectl depuis ton poste

L'API n'est pas ouverte sur Internet : on passe par un tunnel SSH.

```bash
# Récupérer le kubeconfig, une fois (contient des droits admin : ne jamais le partager)
ssh <ADMIN>@<IP_VPS> 'sudo cat /etc/rancher/k3s/k3s.yaml' > ~/.kube/projectos.yaml
chmod 600 ~/.kube/projectos.yaml
sed -i 's#server: https://.*:6443#server: https://127.0.0.1:6443#' ~/.kube/projectos.yaml

# Ouvrir le tunnel (laisser ce terminal ouvert)
ssh -N -L 6443:<IP_VPS>:6443 <ADMIN>@<IP_VPS>

# Dans un autre terminal
KUBECONFIG=~/.kube/projectos.yaml kubectl get nodes
```

## ⚠️ Règle réseau importante

Les NodePorts et `hostPort` **contournent UFW**. Le rôle limite les NodePorts à `127.0.0.1`. N'expose rien d'autre que Traefik.

## En cas de problème

| Symptôme | Action |
|---|---|
| `verify` échoue juste après l'installation | Attendre 2 minutes, relancer |
| Un Pod ne démarre pas | `sudo k3s kubectl get pods -A`, puis `sudo journalctl -u k3s -n 100` sur le VPS |
| Le rôle refuse de s'exécuter | Lire le `fail_msg` : il dit quelle sécurité bloque |

## Retour arrière

Arrêter K3s sans perdre de données :

```bash
sudo systemctl disable --now k3s
```

Tout retirer, seulement si on abandonne K3s :

```bash
sudo ufw delete allow from 10.42.0.0/16
sudo ufw delete allow from 10.43.0.0/16
sudo ufw delete allow 80/tcp
sudo ufw delete allow 443/tcp
sudo rm /etc/sysctl.d/90-projectos-k3s.conf /etc/modules-load.d/projectos-k3s.conf
sudo reboot
```

**Ne jamais** lancer `ufw reset` ou `iptables -F`, ni supprimer `/var/lib/rancher/k3s`.
